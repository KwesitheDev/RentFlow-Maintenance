# Disposable multi-role demo

## Access and deployment

The public entry route is `/demo`; the homepage links to it. No account, email or shared password is required. Choose Owner / Administrator, Property Manager, Tenant or Contractor / Technician. The same workspace can switch perspectives to complete a repair lifecycle.

Use Node 22. In the backend run `npm ci`, configure `.env` from `.env.example`, then `npm start`. In the frontend run `npm ci`, set `REACT_APP_API_URL` to the deployed backend's HTTPS `/api` URL, then `npm run build`. Host the complete `build` directory with the included Vercel configuration: public pages use pre-rendered HTML, `/demo` uses its noindex shell and `/app` uses the private SPA shell. See UI_UX_AND_SEO.md for equivalent routing on other hosts. Set backend `FRONTEND_ORIGIN` to the exact frontend origin. Keep JWT secrets server-only. MongoDB is required by the legacy app and health endpoint; the demo itself operates without MongoDB.

Run a single backend process/replica for this implementation. Demo state is process-local; a restart discards sessions. Do not use round-robin replicas or serverless instances without implementing a shared isolated session store, distributed limits and atomic revision updates. The demo router is mounted before legacy auth and never uses Mongoose models or production JWT secrets.

**External deployment blocker:** hosting credentials/control-plane access have not been supplied. The public deployment and domain routing have not been verified. Local implementation and automated tests are not evidence that the existing hosted service is updated. The complete production brief remains unfinished; see PRODUCTION_READINESS.md.

## Seeds and reset

Every `POST /api/demo/sessions` creates a fresh workspace using `demo/router.js:seed()`. Seeds include two fictional properties, three units, three tenants, a manager, owner, two contractors, eight requests across lifecycle states, assignments, due dates, resolution details and seeded history. Analytics are computed from visible records. Each role has a seeded notification; further notifications and audit events are generated by visitor actions.

Workspaces expire after one absolute hour; expiry is not extended by activity. A minute cleanup timer removes expired state, and every request also prunes it. At most 50 workspaces can exist per process. Reset calls `POST /api/demo/reset` to replace only that workspace's data. Exit deletes the server session; process restart deletes all demo state. No production data or seed scripts are touched.

Opaque 256-bit random bearer sessions are stored as SHA-256 keys server-side. The browser stores the temporary token in sessionStorage, separate from production auth. Tokens are returned only at creation, never logged, and responses use no-store. Use HTTPS in production; bearer-token possession grants access to that disposable workspace. There is no production credential or personal information in the seed.

## Backend permissions

| Role | Visible records | Mutations |
| --- | --- | --- |
| Owner | All fictional properties and requests; reports; audit | Organization display name, create property/unit, submit, assign, valid lifecycle changes, internal/public notes |
| Manager | Palm Court requests, units and reports | Create property/unit, submit, review, assign, valid lifecycle changes, internal/public notes |
| Tenant | Own requests and authorized unit | Submit, public comments, close or reopen resolved repairs |
| Contractor | Personally assigned work | Public comments, start, hold and resolve with resolution details |

Role switching is deliberately allowed only inside the current disposable workspace; all subsequent calls apply that role's permissions server-side. It grants no rights to any production route. Tenant/contractor responses filter internal notes. Inaccessible request IDs return 404. Unsupported mutation fields are rejected. Revision numbers reject stale writes with 409; synchronous validate-then-mutate code serializes updates within the supported single process.

Lifecycle: submitted → reviewed → assigned → inProgress → resolved → closed. Hold/resume, cancellation and reopen transitions are explicitly enumerated. Assignment requires review and a seeded contractor. Resolution requires completion details. Reopening clears the previous resolution timestamp. Every request mutation adds activity/audit events and public changes add recipient-scoped in-app notifications.

No account creation, role administration, external invitations, integrations, mass messages or uploads are exposed. The workspace is bounded to 100 requests and 100 activity events per request. Audit and notification feeds retain the most recent 500 events each. Per-IP demo limits: 120 calls/minute and 10 session attempts/minute. Capacity exhaustion returns 503. Client IP uses Express's default trust-proxy setting; behind a shared proxy this may aggregate visitors. Configure a narrowly trusted proxy only after validating the platform's forwarded IP behavior. Do not blindly enable trust proxy.

## Verify

Run `npm test` in the backend and `CI=true npm test -- --watchAll=false --runInBand` in the frontend, followed by `npm run build`.

Manual hosted acceptance: launch as tenant, submit a Palm Court A-101 leak, switch to manager, open the new request, mark reviewed and assign Esi. Switch to contractor, start then resolve with details. Switch to tenant and close or reopen. Verify notifications and owner reports/audit. Launch another workspace in a separate browser and confirm the new request is absent. Test narrow/mobile screens, keyboard navigation, expiry, reset, unavailable backend and invalid API mutations before advertising the public URL.

Current limitations: production invitations/uploads are not showcased; the demo offers seeded property/unit/team inventory, property creation with an initial unit, and owner display-name editing. Demo property creation is capped at ten properties. A local Chrome smoke test covers the real demo API lifecycle. Hosted and production end-to-end verification remain outstanding. Analytics cover counts, overdue work, completion rate, mean resolution hours, priorities, properties and contractor workload; time-series/date filters are pending.
